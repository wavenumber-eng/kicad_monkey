# Log: native-acceleration-options-research

Compared parser/tokenizer acceleration directions using the fresh Jumperless
decomposition and current KiCad API direction.

## Fresh performance basis

On Jumperless, raw regex scanning is best `1.119s`, full token production is
best `9.541s`, and `parse_sexp()` is best `11.654s`. That means a native
scanner alone can at most address a small part of full parse. The larger
opportunity is avoiding or accelerating `SexpToken` object allocation and
generic tree materialization.

## Options

1. Pure-Python pull parser / streaming typed parser.
   - Pros: no wheel, ABI, compiler, or platform packaging cost; directly
     attacks token-list and tree materialization; keeps Python as the reference
     implementation.
   - Cons: parser architecture change; must preserve current error locations,
     token semantics where public, round-trip behavior, and typed factories.
   - Current ranking: evaluate first. It sets the baseline native options must
     beat.

2. C tokenizer accelerator.
   - Pros: small surface area; could speed raw scanning and optionally emit
     compact token structs.
   - Cons: raw scan is already about `1.119s` on a 28 MB board; if it still
     returns millions of Python `SexpToken` objects, it leaves most cost in
     place.
   - Current ranking: useful only if coupled to a pull parser or compact token
     stream that avoids per-token Python object creation.

3. C++ tokenizer/parser accelerator.
   - Pros: aligns with a future native core or possible KiCad-format parser
     direction; can combine scanning, validation, and tree/typed event output.
   - Cons: largest packaging and maintenance burden; C++ ABI/toolchain issues
     on Windows/macOS/Linux; must not fork behavior from Python golden corpus.
   - Current ranking: plausible future port, not first implementation step.

4. Cython over current Python structures.
   - Pros: lower migration cost than a full C/C++ port; can accelerate tight
     loops while keeping source close to current implementation.
   - Cons: still has native wheel cost; less useful if the bottleneck remains
     Python object materialization; can obscure reference behavior.
   - Current ranking: secondary option after pure-Python architecture.

## KiCad API direction

Official KiCad developer docs state that SWIG-based Python bindings are
deprecated as of KiCad 9.0 and planned for removal in KiCad 11.0, and that the
IPC API is the modern stable interface. The IPC API uses Protocol Buffers and
NNG, is language-agnostic, and in KiCad 9/10 is centered on communicating with
a running KiCad instance rather than exposing a standalone file-loading
library.

Primary sources:

- https://dev-docs.kicad.org/en/apis-and-binding/pcbnew/index.html
- https://dev-docs.kicad.org/en/apis-and-binding/index.html
- https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/index.html

Implication for this plan: do not frame a native accelerator around KiCad's
deprecated SWIG bindings. If C++ alignment matters, it should mean an internal
validated native parser core or IPC/protobuf awareness, not a dependency on the
legacy `pcbnew` binding model.

## Recommendation before independent review

Proceed with research handoff before implementation. The tentative direction is
documentation/guidance first, pure-Python pull/parser architecture as the first
serious full-parse lever, and native acceleration only as a later validated
accelerator behind the same corpus and API contracts.
