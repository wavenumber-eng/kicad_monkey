## Findings

1. **`_LineColumnIndex.__init__` builds the newline index with a per-char
   Python `enumerate` loop** - the exact anti-pattern the accepted lexer
   checklist calls out. Measured on WREN (57.7M chars, 1.9M newlines):
   `enumerate` 1.10s vs `re.finditer(r"\n")` 0.14s vs `str.find` loop 0.19s
   (all three produce identical offsets; verified). ~1s avoidable one-time
   cost per projection on the largest board (~4% of the 22.5s nested
   result). Recommended fix: build with `re.finditer` (or `str.find` loop).
   Small, safe, and the existing oracle test already gates it.
2. **The `sexpr-lexer-tokenizer-optimization` step is marked done, but the
   implementation is constant-factor loop tightening, not the accepted
   candidate #2.** Checklist items 1-4 from the research review (compiled
   master regex alternation, delimiter jumps, lazy unescape, regex-group
   number classification) are unimplemented - confirmed in the current
   `kicad_sexpr.py`: quoted strings still walk per-char via `raw.append`,
   numbers still classified per-atom via `_NUMBER_TOKEN_RE.match`, no
   `finditer`/`str.find` jumps. Measured full-parse gains are 1.29-1.77x vs
   the recorded 3-8x pure-Python expectation; WREN full parse remains 25.2s
   and common-families 35.3s. The docs describe what was actually done, so
   this is a scope question, not an integrity problem. Options for the
   user: (a) require the regex-tokenizer rewrite before closeout, or
   (b) accept current gains, re-title/annotate the step, and record the
   regex tokenizer as explicit deferred work alongside the native options.
3. Minor, carried over from the first review (style only, audit passes):
   exit-criteria ids `design-doc-intent-audit`, `test-runtime-impact-audit`,
   and `external-review` collide with step ids and break the `ec-` prefix
   convention.
