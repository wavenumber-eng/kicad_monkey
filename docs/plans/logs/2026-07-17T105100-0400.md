# Log: render-pipeline-architecture-research

Reviewed whether current IR/SVG paths can safely become projection-backed or
whether they need new file-level APIs.

## Current render pipeline facts

- `KiCadPcb.to_ir()` delegates to `pcb_to_ir(self, ...)`, where `self` is
  already a full `KiCadPcb`.
- `KiCadPcb.to_svg()` delegates to `render_pcb_ir_to_svg(self, ...)`, where
  `self` is already a full `KiCadPcb`.
- `render_pcb_ir_to_svg()` computes an all-layer bounding box first, builds a
  complete PCB IR document with `pcb_to_ir(pcb, ...)`, then applies optional
  layer filtering to records before `render_ir_to_svg(...)`.
- `pcb_to_ir()` walks full board collections in a stable order:
  graphics, tracks, vias, tables, dimensions, zones, then footprints.
- Enriched PCB SVG metadata depends on full-board/project context including
  source path, project text variables, net classes, layer metadata, net
  metadata, pad/via hole details, and record extras.
- Schematic `schematic_to_ir()` similarly consumes a full `KiCadSchematic`
  object and emits records in KiCad-natural order.

## Feasibility assessment

Do not rewrite existing `to_ir()` or `to_svg()` methods to call projection
internally. Those methods run after full object materialization and would add
complexity without saving the parse cost.

Potential new file-level IR/SVG APIs are possible only as a separate design
and must prove the following before promotion:

- stable KiCad draw order for all included object families;
- all-layer versus selected-layer bounding box semantics;
- zone, filled-polygon, pad, via, slot, mask, paste, drill, and board-outline
  behavior;
- source IDs and enrichment metadata parity where the API claims enriched SVG;
- project text variables and net classes when a project sidecar is present;
- behavior for omitted object families if a partial API is intentionally
  selected-layer or selected-family only.

## Candidate shape

The lowest-risk implementation path, if accepted after review, is not a hidden
change to `KiCadPcb.to_svg()`. It is a new explicit file-level API such as:

- `pcb_file_to_ir(path, *, layers=None, profile=None)` for reviewed supported
  subsets; or
- `render_pcb_file_to_svg(path, *, layers=None, profile=None)` as a facade over
  that path.

The design may still reject these APIs if parity cost is too high. If rejected,
close the implementation step with a recorded rejection and improve guidance
instead.
